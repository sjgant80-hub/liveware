How it works — the path every run took
  1. Pin public data, split it once. Two public datasets from the UCI Machine Learning Repository, fingerprinted by SHA-256 so nobody can swap them, shuffled once by a fixed seed: half to learn from, a quarter to check rules on, a quarter held back as the final exam.
  2. The AI teaches — once. A seven-billion-parameter model on our own machine (qwen2.5:7b, no cloud) reads 40 labelled examples and writes rules like “gill colour is buff → poisonous” (one it really wrote, and one the gate kept). Models don't repeat themselves word for word, so its reply was recorded the one time it answered. That is the one step you can't re-run here, and this page doesn't pretend you can.
  3. The gate keeps only what holds up. A rule survives only if, on the check split, it applies often enough (15 times; 12 for combined rules) and is right at least 80% of the time. Everything else is thrown out, in the open.
  4. The exam decides. The surviving rules — plain code, no AI, free to run on any computer — answer the final exam. The baseline is the simplest thing you could do without us: always guess the commonest answer.
  5. The guarantee signs. The baseline agreement was fixed before the work. It says “due” only if the rules beat the baseline by at least 8 percentage points, on the whole exam, by a clear statistical margin (a two-proportion z-test at z ≥ 1.96 — about 95% confidence that the gain is not luck); otherwise “waived”. The receipt is a SHA-256 fingerprint of that sealed test and both scores — change either and it changes.

The audit trail is public. Every run leaves one: the sealed plan, the AI's recorded reply, the result, and its receipt, each a public commit on GitHub that can't be altered afterwards without changing its fingerprint. And a third party re-checks it: GitHub's own runner re-derives this exact receipt on every change to this page, and fails the build if it doesn't match.

Proves: the guarantee says “due” only when a delivery beats the signed baseline on data nobody used to build it — and says “waived” when it doesn't, twice, on the record. Every number re-derives in your browser, and changing the exam changes the receipt. Doesn't claim: that the AI step re-runs here (it was recorded once), or that it will beat your baseline — two of these three didn't. The mushroom rules are classroom data, not advice.

How it works

Five moves, one loop. A signed seed grows the system; a door on the raw bytes defends a deliberately naive core; LIGHT keeps everything small and lossless; a mesh lets two copies find each other with no server; and every step writes a receipt anyone can re-run. The organism grows, defends, compresses, meshes and proves — then reproduces a verified copy of itself. Each panel below ends with a line from GitHub's published run of that step.

The seed

Magic, length, a LIGHT-encoded genome (every block pinned by SHA-256), a seal, and an Ed25519 signature over everything but itself. It checks magic, length, decode, shape, seal, signature, then each block's hash — only then does a block load.

—

The door & immune system

A signed-packet door checks size, magic, version, length, dictionary, sender, signature and replay counter on the raw bytes before the body is decoded. Every refusal mints two antibodies: the exact bytes, and their shape.

—

LIGHT compression

A context-mixing arithmetic coder — seven models blended by weights that learn as they go, integer-only so encoder and decoder agree bit for bit on every engine, and lossless back to the original.

—

The mesh

Each tab has its own key; they meet over the browser's channel (trust-on-first-use pins the key), then every message is a signed LIGHT packet checked against that key and a replay counter, with one shared document merged by a conflict-free law.

The white paper — the method on one page

1 · The problem

AI software is sold on claims a buyer can't check: benchmark scores nobody else can re-run, demos nobody is allowed to break, and “trust us” on where the data goes. A claim that only its maker can reproduce is marketing, however true it happens to be.

2 · The method

  1. Seal the test first. The pass criteria are written and committed before any code that measures them exists (CLAIMS.md, and CLAIMS-T11.md for the guarantee). The harness refuses to run if a sealed file has changed since the commit that sealed it, so the goalposts can't move after the result is known.
  2. One test body, run in two places. Each test is written once and imported both by this page and by the harness on GitHub's runner. What your browser runs is the code that was gated, not a demo of it.
  3. Receipts, not screenshots. Each run writes a record of its inputs, its outputs and its verdict; the receipt id is the SHA-256 of that record as canonical JSON. Two runs agree exactly when one short string agrees.
  4. Tests that can fail. The witness mutation gate plants a bug in every kernel and fails the build unless a test catches it. A mutant may be let through only with a written, checked reason — and the gate's own figures are a receipt GitHub re-derives.
  5. Losses stay on the record. Weak compression rows, the two guarantee runs that lost, and every “doesn't claim” stay on the page beside the wins.

4 · The limits

  • The guarantee's AI step is not re-run here: a model's reply is not reproducible word for word, so it was recorded the one time it answered. Everything after it re-runs.
  • The mesh joins tabs in one browser. A second device needs a relay and is not claimed. First contact is trust-on-first-use.
  • The door does not protect stolen keys or a stolen device — that is a different layer.
  • LIGHT is smaller, not faster: it is slower than gzip and zstd, and the time is shown.
  • Wave 2 — memory, self-improvement, the thinking organism, structural alignment, cache reuse — is not proven on this page. It is marked IN BUILD, with no green light, until each piece has its own sealed test and button.
  • The guarantee's data is public classroom data. Beating a baseline there says nothing about your process until your own baseline is signed and your own exam is sat.

5 · Why it matters to a buyer

When the test is sealed before the work and the result is a receipt anyone can re-run, the buyer stops having to judge the supplier and only has to judge the test. That moves the risk to where it belongs: on the work, not on the trust.

    FAQ

    Is this real or a demo?

    Every claim on this page runs live in your browser and gives you a receipt you can check. The same tests run publicly on GitHub and get the same answers.

    Does any of my data leave my device?

    No. The page works offline once loaded. Files you drop in are processed locally and never uploaded.

    Why do you show the tests that fail?

    Because a record that includes its losses is one you can believe. The compression rows where LIGHT barely wins stay on the table; any failed claim stays on the page.

    Do I need a powerful computer?

    Most tests run on any modern browser, on plain CPU. The AI tests (Wave 2) need a browser with WebGPU; if yours doesn't have it, they're skipped and marked.

    What is “teacher distillation”?

    A large AI model (the teacher) is used once, at build time, to propose rules from examples. Plain code then keeps only the rules that hold up on data the teacher never saw. What ships is small, fast and fixed — it runs on any computer, needs no AI to answer, and costs nothing per use. The expensive model is paid for once, not on every request.

    When I press re-run, does the AI run again?

    No, and we say so plainly. A model's reply isn't reproducible word for word, so the teacher's reply was recorded the one time it answered, and committed with the result. Your browser re-runs everything after that — reading the rules, the check, the exam, the signed verdict — and must land on the committed receipts. You can read the recorded reply on the page.

    Why show two runs that lost?

    Because a guarantee that can't say no is worthless. On the car data the AI's rules didn't beat the simple baseline, so the charge was waived — twice. Those runs stay on the page beside the one that won, with their own sealed commits.

    Can I use this for my company?

    Yes. Start with one process and a signed baseline — see “For business” above.

    Is it open source?

    Yes. The code is MIT — the licence is in the repository — and so is fall-kit, where the vendored kernels come from. The public datasets and the sample files keep their own terms; the UCI datasets are credited below.

    What is a receipt, exactly?

    A record of what a test fed in, what came out and its verdict, written as canonical JSON (keys sorted, so the same record is always the same bytes). The receipt id is that record's SHA-256 fingerprint. Change one byte of the inputs, the outputs or the verdict and the id changes completely — which is why matching ids mean matching runs.

    Who checks the checker?

    The witness mutation gate. It plants deliberate bugs in each kernel, one at a time — turns a > into >=, an && into ||, a return true into return false — and fails the build unless a test catches every one. The blueprint shows each kernel's figures, read from a gate receipt that GitHub's run re-derives on every change.
